# CHAOS JSON 增量交换 v1

首版按用户选择提供**同一 Wi-Fi 下的电脑与手机直连**，不要求云服务。用户主动开启短时连接并由接收端确认写入；没有后台自动同步。离线时也能使用 UTF-8 JSON 文件或粘贴 JSON。两种传输都使用同一份协议并调用 `exchange.preview`／`exchange.apply`，不另写业务状态。

## Wi-Fi 直连步骤

1. 两端连接同一 Wi-Fi，并各自打开本机 Markdown 工作目录。
2. 电脑“设置 → 设备增量交换 → Wi-Fi 直连”选择手机能访问的本机地址，点击“开启 Wi-Fi 连接”。首次可能需要允许 Windows 防火墙的专用网络访问，不修改或开放普通业务服务端口。
3. 把电脑显示的完整配对连接输入手机的“电脑配对连接”。手机点击“读取电脑变化”，检查预览后“确认导入电脑变化”；回执自动返回并缓存共同版本。
4. 手机有新内容时点击“发送手机变化”。电脑设置会显示预览，电脑点击“确认导入手机变化”才写入，回执随后自动返回手机。也可拒绝该次变化。
5. 连接可以手动关闭，30 分钟后自动关闭；退出电脑程序或切换工作目录也关闭。重新开启会生成新的密钥和端口，手机输入新的配对连接即可继续使用已有共同版本。配对连接只缓存在当前应用会话，不进入业务数据或交换文件。

连接中断时没有确认的业务写入不会偷偷执行。已成功写入但未收到回执时，可重新读取／发送，相同 UUID 和内容会跳过；不能用网络超时判断业务一定没有提交。电脑与手机同时修改同一对象或同一业务线 Notes 时首版不自动合并，先人工核对并在文件级统一内容，再重新建立共同版本。

连接仅支持局域网 IPv4。访客 Wi-Fi 的客户端隔离、VPN 和防火墙可能阻止两台设备互访；请选择实际 Wi-Fi 地址，不能选择无关虚拟网卡。未验证实体手机与具体路由器的连通性。

### 网络封装

普通本机业务服务仍绑定 `127.0.0.1` 并保留会话鉴权。另一个独立、临时的监听器绑定用户选择的本机私有地址和随机端口，只接受 `/chaos-exchange/<会话 UUID>` 上的加密 POST；不提供目录浏览、任意业务命令、文件访问或远程确认写入。

配对连接的 fragment 保存随机 128-bit 密钥；该密钥不作为 HTTP 参数传送、不写日志、不持久化在工作目录。请求和响应使用 AES-GCM，随机 12-byte IV，方向与请求 UUID 作为附加认证数据。网络外层为 JSON `{version:1, requestId, iv, payload}`，后两项使用 Base64；`payload` 才是加密后的拉取、提交、回执等消息，内部变更包仍是下述 `chaos.exchange` v1。会话拒绝请求重放，接收端限制大小、超时、重定向、公网目标和非协议路径。

Android 的受限原生桥访问局域网 HTTP，业务正文已由共用协议加密；不放宽 WebView 的混合内容策略。Android manifest 开启 HTTP 传输仅用于承载该密文，桥限制为私有 IPv4 和固定协议路径。配对连接持有者可读取该工作目录的受管内容，因此不要公开配对信息。协议不是公网服务或账号体系。

## 离线文件步骤

1. 电脑和手机各自连接本机 Markdown 工作目录，在“设置 → 设备增量交换”操作。
2. 发送端点击“生成发送包 → 保存发送包”。首次没有共同版本，发送全部受管记录和正文；普通文件和附件不包含在内。
3. 接收端“打开交换文件或回执”，检查新增、更新、相同、冲突和缺失关联。无冲突后点击“确认导入并生成回执”。整包一次发布，不部分导入。
4. 接收端保存回执并传回发送端，发送端载入回执。只有对方确认成功才推进共同版本，生成文件本身不表示已送达。
5. 后续发送只包含相对于该回执变化的对象。接收端也可以使用同一回执反向发送。双方按顺序交换最新回执；过期回执可能导致冲突，不会覆盖新内容。

设置会按本机目录缓存最近的回执，只含 UUID 和共同内容哈希，不含正文，不是第二份业务数据库。浏览器缓存清除、设备更换或目录搬迁后，重新载入已保存的回执；丢失回执可清除共同版本后再次发送，内容相同自动跳过，内容不同必须先人工核对。首版每个目录只缓存最近一个交换通道，多设备时自行选择相应回执。

## 标准格式

媒体类型 `application/json`，编码 UTF-8；文件名建议 `CHAOS-changes-<id>.json` 或 `CHAOS-receipt-<id>.json`。字段结构由 [JSON Schema（2020-12）](chaos-exchange-v1.schema.json)和 `packages/domain/exchange.ts` 定义，运行 `npm run schema:exchange` 重新生成。标准业务 API 的 `/api/business/v1/schema` 同时公开命令结构。

| 字段                  | 含义                                                                           |
| --------------------- | ------------------------------------------------------------------------------ |
| `format`、`version`   | 固定 `chaos.exchange`、数字 `1`；不兼容版本直接拒绝                            |
| `kind`                | `bundle` 为变更包，`receipt` 为成功导入回执                                    |
| `id`                  | 包／回执 UUID，不使用时间戳作为身份                                            |
| `channelId`           | 一次交换关系的 UUID，由首包生成并由回执延续；不是设备路径或 `Snapshot.vaultId` |
| `createdAt`           | ISO 8601 UTC 时间，仅用于说明，不裁决新旧                                      |
| `baseline`            | 发送所依据的回执哈希表：`对象 UUID → 共同版本 SHA-256`                         |
| `manifest`            | 发送端当前全部受管对象 UUID 和内容哈希，不含文件路径                           |
| `changes`             | 本次变化；每项含 `operationId`、`data`、`body`、`baseHash`、`hash`             |
| `missingIds`          | 共同版本中存在、发送端现已缺失的对象；仅提示，**不是删除命令**                 |
| `hashes`、`packageId` | 仅回执：确认的共同版本和所确认的包 UUID                                        |
| `checksum`            | 整个包（除本字段）的 SHA-256 完整性校验，不是签名或加密                        |

`data` 直接采用现有领域记录 Schema，覆盖项目、业务线、节点、TODO／IDEA、实际、资源元数据与回顾。`body` 是受管 Markdown 的正文，包括业务线 Notes、节点纪要和条目批注，保持单一原文。新旧记录使用稳定 UUID 匹配，不通过名称或时钟推断身份。同名不同 UUID 只列为匹配候选，默认明确新增，绝不自动合并或改写引用。

每个对象的 `hash = SHA256(canonicalJson({data, body}))`。受管笔记资源的 `data.target` 使用 `chaos-note:<UUID>` 逻辑标识；存储路径由接收端决定，新笔记写入 `ATLAS/knowledge/imported/<UUID>.md`，已有笔记保留本机路径。包不能指定写文件路径、`FileChange` 或运行日志。其他资源引用保留原契约，但附件不传输，电脑外部路径不会在手机突然变得可用。

`canonicalJson` 递归按对象键的 JavaScript 字符串顺序排序，数组保留顺序，标量使用标准 `JSON.stringify` 表达；输入是 Schema 校验后的 JSON，不含 undefined、NaN 或循环引用。UTF-8 编码后计算 SHA-256。哈希包括记录时间字段和正文原有换行，不使用文件修改时间或本机原文 revision。顶层校验也用相同的规范化方法，排除 `checksum` 后计算。

外部生成器先按 Schema 补齐字段与默认值，再计算各对象哈希、清单及整个包的校验。结构校验不能代替校验值、UUID 唯一性与跨对象业务校验；推荐通过共用 `WorkspaceService` 生成，而不是手动拼接哈希。现有 `plan.create` 仍是文本识别后快速创建计划的业务入口；日后识别器可把结构化对象包装成这个交换格式，先预览再确认。

## 匹配、冲突与原子性

- 同 UUID 且本机内容哈希等于传入 `hash`：重复或已一致，跳过，不重写时间、正文与 Markdown。
- 本机不存在且 `baseHash=null`：新增；必须同时具备所需父级、Notes 和待办池，或这些对象已存在于本机。
- 本机哈希等于 `baseHash`：允许更新；说明本机仍停留在双方共同版本。
- 同 UUID 两侧均变化、非法类型变化、旧对象本机已删除、Notes／待办池身份被替换：冲突，整包不写入。不提供“按最新时间强行覆盖”。TODO／IDEA／普通节点升为业务线属于已有合法类型变化，沿用共用升线判定，并一并传递 Notes、待办池及关联变更。
- 预览版本绑定包校验值、当前目录会话以及全部原文 revision；确认前文件发生变化或更换了包，必须重新预览。真正发布仍再次验证原文件版本。
- 共享交换服务经过 `WorkspaceService` 和 `Workspace.applyBatch`，沿用领域关联校验、实际时间不重叠、Notes 约束和平台可恢复批次发布。对象和正文一并提交；传输层只读写 JSON。
- 回执只把确实一致／成功写入的内容标为新的共同版本。接收端独立修改而本包未涉及的对象仍保留旧共同版本，下一次可反向增量发送。

## 首版明确限制

只同步受管记录及正文的新增和更新。不自动传播删除，不建立删除墓碑、历史库或自动备份；双方需手动核对删除，旧对象在接收端被删后也不允许旧更新将它复活。缺失的共同对象可能阻止其他有依赖的增量导入，此时先人工核对，再重新建立全量共同版本。

不复制附件、普通非受管 Markdown、外部 YAML 字段、配置、密钥、锁、待发布日志或 QQ 消息来源状态。接收端已有非系统 YAML、BOM 和文件布局通过现有 Markdown 更新器保留；正文采用用户确认的来源正文，正文换行变化也算变化。外部 YAML 若需要两端一致，请使用原文件的手动完整目录转移。

单包最多 512 KiB、1000 个受管对象，超限明确拒绝，首版不截断、不分页发布、不支持分片二维码。离线 JSON 文件包含用户主动导出的业务正文，文件本身不加密或签名，传递渠道由用户选择；Wi-Fi 外层提供上述配对加密。两种方式的业务写入均由接收端检查确认。
