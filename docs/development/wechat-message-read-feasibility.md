# 微信 4.x 本机消息读取可行性验证

验证日期：2026-11-04。范围为当前已登录的本人微信账号及本机 `xwechat_files`；本阶段全过程只读，未输出或保存消息正文、会话 ID、联系人 ID 或密钥。后续已将只读文字消息接入 CHAOS 自动同步。

| 字段    | 本机验证结果                                                                                     | 接入时的处理                                                                                                  |
| ------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 会话 ID | `contact.username` 可对应 `Msg_<username 的 MD5>` 消息表；一个会话可跨多个 `message_N.db` 分库。 | 用微信内部 ID 绑定会话，不用显示名称作主键；跨分库合并。                                                      |
| 消息 ID | `server_id` 与 `local_id` 可读。抽样发现跨分库的 `local_id` 重复。                               | 不能仅用 `local_id` 去重；保留分库标识，优先使用有效的 `server_id`。                                          |
| 正文    | 抽样群文字消息均可解码为非空 UTF-8；部分正文使用 zstd 压缩。                                     | 按压缩标记解压；首期仅处理文字消息。                                                                          |
| 发送人  | 最近群聊样本的 `real_sender_id` 均可在所在分库的 `Name2Id` 中解析。                              | 必须使用消息所在分库的索引，不能跨分库套用数字 ID。                                                           |
| 时间    | 最近群聊样本均有合理的 `create_time` 时间戳。                                                    | 保留原发送时间，按分库与消息 ID 建立增量游标。                                                                |
| @ 信息  | 样本来源元数据中存在 `atuserlist`；可解析出 @全体 和 @本人。部分来源字段需 zstd 解压。           | 根据结构化名单判断真实 @，不只看正文中的 `@` 字符。本人 ID 需去掉账号目录名末尾的本机后缀，并用联系人库核对。 |

密钥验证覆盖 `contact.db` 和多个 `message_N.db`，均通过；另验证了 `session.db` 与 `general.db` 可解密。联系人姓名可能重复：同名/备注搜索可能得到多个结果，而微信号精确匹配唯一，因此会话绑定应使用内部 ID。

结论：现有本机数据库足以提取 QQ 流程所需的微信文字消息字段，并复用消息筛选、AI 识别和待确认应用服务。接入后在隔离工作目录验证了近期私聊文字消息进入待确认，第二次同步未重复生成；读取时已处理数据库 WAL。新消息实时到达、长时间运行和微信升级后的结构兼容性仍需实际使用中继续观察。
